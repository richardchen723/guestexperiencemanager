# Ticket 847: data audit and owner access

The owner portal combines isolated owner access with the approved visual performance dashboard and an explicit finalized-statement publication workflow. The access foundation and original audit are documented first; current reporting and publication behavior are described below.

## Boundary

owner_portal.app:create_app is a separate Flask app, started by wsgi_owner.py. It never imports the staff app, staff sessions, Hostaway source models, or bookkeeping routes. It has a separate Google OAuth client, signing secret, __Host-owner_portal cookie, OS service user and database login. The approved public URL is https://yourcottoncandy.com/owners. Nginx sends that path to the separate service; OwnerMount handles a fixed path prefix without trusting forwarded-prefix headers. Path hosting shares a browser origin with the staff app, while authentication, process and database boundaries remain separate. The factory does not run migrations. Startup rejects a database credential with superuser/role-administration privileges or readable/writable business tables outside the owners schema.

Owner accounts represent households or companies. Individual identities are keyed by verified Google subject, never by a staff role or email lookup. Memberships give separate performance and finalized-statement permissions. Property grants define the exact physical property and reporting interval [from, until). An open-ended grant has no until. Reporting history is independent of invitation acceptance or sign-in time; prior-year comparison reads must satisfy the same interval checks. Revoking membership ends existing sessions; account, membership, property and grant status are checked when serving data. A new invitation can explicitly restore revoked membership.

Physical properties may have several alternative listings, all verified by staff to describe the same unit. Each source listing can map to only one property. Bundle listings are deliberately unsupported in this phase and must remain unmapped until allocation rules are implemented. A portfolio label is only a display grouping. Neither operating/bookkeeping portfolios nor Sales CRM relationships grant access. No existing CRM contact is automatically enrolled and the internal owner superadmin role is never used for property owners.

/api/context returns a small explicit allowlist: accounts, permissions, property display names, currency, timezone, and reporting bounds. It does not return listing IDs, emails, Google subjects, source reservation records, guest identities, messages, financial source rows, or internal staff notes. Reporting handlers call authorize_property before querying prepared owner data; totals, comparisons and downloads respect the authorized property set and interval. Published statements use frozen recipient/property scope and immutable application versions in addition to the membership flag. No internal application endpoints are registered.

## Read-only source audit

Run with a deliberately selected source credential. It opens a repeatable-read, read-only transaction with a per-query timeout; it never initializes the staff app or reads guest/message fields, raw calendar payloads or statement contents.

~~~bash
OWNER_AUDIT_DATABASE_URL="$READ_ONLY_SOURCE_URL" python -m owner_portal.audit --environment 'Name and freshness of source snapshot' --as-of 2026-10-30 --output /private/path/owner-audit.json
~~~

The output file must not already exist and is created with mode 0600. Keep actual source evidence private, outside version control. It reports listing metadata gaps, date/status quality, per-channel financial field presence (unknown and zero remain distinct), potential duplicate source references/shared addresses, monthly history coverage, latest calendar coverage per listing, independent portfolio mappings, bookkeeping revision availability, and owner/CRM schema availability. A shared address is a review candidate, not proof of duplicate units.

The finance presence section counts new, modified, and confirmed reservations overlapping the audit window. These are candidates for review, not a certified financial dataset; customIcal, zero-priced rows, ambiguous bundle mappings, refunds, taxes and deposits still require source interpretation. Monthly coverage uses arrival month and is not a stay-night revenue/occupancy calculation. Missing source tables are reported as unavailable. An incompatible existing table fails the audit rather than producing misleading partial totals.

The first local snapshot audit is saved in ignored output/owner-847-qa/ for review. It is not production verification. Before enabling performance: verify canonical accommodation revenue per channel against source evidence; hydrate or explicitly validate timezone/currency; approve physical-unit/bundle mapping; classify unavailable nights; and expand/sustain calendar history. The recently merged finance-sync and occupancy fixes remain unchanged by this work. Finalized owner statements still need a separate publication workflow from approved bookkeeping revisions. Forecasts and honest prior-year comparisons remain later milestones.

## Explicit setup

1. Migrate with an administrator credential: OWNER_ADMIN_DATABASE_URL=... python -m owner_portal.cli migrate. This creates only the additive owners schema, tables and indexes. It creates no owner identities, grants, or invitations. Repeating it is safe for this initial schema; future schema changes require explicit migrations.
2. Have the database administrator create a dedicated, non-inheriting login with no memberships, superuser, database/role creation, source-table rights, or executable privileged functions. Generate its grants with python -m owner_portal.cli runtime-sql --role owner_portal_web and apply the reviewed SQL. Do not supply staff database credentials to the owner service. The owner runtime can update authentication records but cannot grant property access or read source business tables. The startup check is a guard against table privilege mistakes; DBA review must also cover role memberships and executable security-definer functions.
3. Configure the owner service independently:

   ~~~text
   OWNER_PORTAL_DATABASE_URL=<restricted PostgreSQL login>
   OWNER_PORTAL_SECRET_KEY=<independent random secret, at least 32 characters>
   OWNER_PORTAL_ORIGIN=https://yourcottoncandy.com
   OWNER_PORTAL_PATH_PREFIX=/owners
   OWNER_PORTAL_LOGIN_ENABLED=false
   OWNER_GOOGLE_CLIENT_ID=<dedicated OAuth client>
   OWNER_GOOGLE_CLIENT_SECRET=<dedicated OAuth secret>
   ~~~

   Configure the exact Google redirect URI as https://yourcottoncandy.com/owners/auth/google/callback. Keep OWNER_PORTAL_LOGIN_ENABLED=false until the real owner OAuth client is configured and verified; the public page then explains that sign-in is being prepared, all authentication handlers reject requests, and staff invitation creation is disabled. Set the same readiness flag on both services when activating it. The app uses authorization code + PKCE, browser-bound single-use state, verified signed ID tokens, nonce, audience/issuer checks, and verified email matching the invitation. It binds later sign-ins to the Google subject. Tokens expire server-side after 12 hours; sign-out revokes the session. See [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) and [ID-token validation](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

4. Create a dedicated hostaway-owner system user and install deployment/hostaway-owner-portal.service with an isolated, root-readable /opt/hostaway-messages/owner-portal.env. The service binds only 127.0.0.1:5011 and cannot read staff environment files, guest storage, or release backups. Install deployment/nginx-owner-http.conf in the Nginx http context and the proxy/locations snippets at the paths documented in those files. Include the locations snippet in the existing HTTPS server; preserve the original /owners path and Host header. Test Nginx before reload. Owner OAuth endpoints are rate limited and owner access logs exclude query strings and bodies. The owner service omits Gunicorn access logging so OAuth codes are not logged there. Apply normal retention to consumed/expired login flows and sessions; preserve access audit events.
5. After migration, set OWNER_ACCESS_ENABLED=true and the same OWNER_PORTAL_ORIGIN, OWNER_PORTAL_PATH_PREFIX and OWNER_PORTAL_LOGIN_ENABLED on the staff app. Approved human admins see **System → Owner access**. The setup feature is disabled by default and rejects API keys, service identities, unapproved/inactive users, and missing CSRF tokens.
6. Create an owner account, register verified physical properties, set each reporting grant, and create one invitation per person. Links expire after seven days; only their hashes are stored. The raw link is shown once, with its token in the URL fragment so it does not enter HTTP access logs. The owner page removes the fragment and stages the hash before Google sign-in. Send the link only to the intended verified contact address through an approved channel; Google email verification alone is not proof of current control of a third-party email address. This implementation generates links but sends no email. A replacement invitation invalidates previous pending links. Use the staff read-only preview and revoke controls to verify access. Preview is audited and never creates an owner session.

Activation is explicit: configure/test the real OAuth client, restricted role, proxy routing and a reviewed pilot mapping before enabling owner sign-in. No owner assignments or invitation deliveries are automatic. Roll back the release-owned code/configuration, disable the staff flag and stop the separate owner service; preserve the schema and audit records. Source operational evidence and deployment journals stay outside this public repository.

## Performance dashboard and finalized statements

The second implementation replaces the preparation screen with the approved visual snapshot: stayed/confirmed/estimated revenue, sellable-night occupancy, six monthly columns with prior-year markers, a property breakdown, and finalized statements. The account, property and month controls operate under `/owners`. Definitions stay collapsed; chart values are also available as an accessible table. Figures are always USD. Property-care/approval cards are omitted until those have an owner-safe source.

`GET /api/dashboard` uses only `owners.performance_months` after rechecking membership, property status and the entire reporting month. Every prior-year month is separately authorized. All-property totals require complete values for the same selected set; no silent partial sums or historical clipping. A midmonth grant makes that full month unavailable. The default is the earliest whole month common to the selected grants, at or after the current month. Stale preparations (>48 hours) remain labeled; future forecast values are withheld. Revocation is enforced on every refresh and document request, with no shared response caching.

The offline `python -m owner_portal.prepare` worker uses `OWNER_PREPARE_DATABASE_URL` and separate `HOSTAWAY_ACCOUNT_ID`/`HOSTAWAY_API_KEY` environment settings. It never loads staff configuration. Create a dedicated non-inheriting role and apply `python -m owner_portal.cli prepare-sql --role owner_portal_prepare`. These grants cover explicit source columns, sanitized aggregate writes and a worker-only financial cache. The owner web role gets SELECT on prepared months and published statements only, and cannot read the finance cache or source tables. Run the additive migration and updated runtime grants before starting the new web version. No DDL runs during web startup.

`deployment/hostaway-owner-reporting.service` and its hourly timer use a separate OS user and root-private `owner-reporting.env`. The worker's Hostaway calls are read-only. It refreshes live future calendar dates through the displayed horizon rather than assuming the staff pipeline's 60-day calendar is sufficient. Existing historical calendar snapshots supply booking pickup. Sanitized owner-worker calendar observations are retained separately, with no raw payloads and no owner-web read permission, so longer lead-time history can accumulate beyond the staff feed’s 60-day horizon. Financial cache entries are invalidated by source identity/dates/status/amount/update changes; unchanged successful amounts are rechecked weekly and unresolved amounts daily. No raw API responses, guest identities, notes or messages are stored in the owner schema. Source credentials never reach the owner web process. The worker serializes runs, commits complete property snapshots, and fails without overwriting that property's previous aggregates on database errors.

The worker prepares every month from the available reservation history (and at least 26 prior months) through three future months. It backfills recent historical calendars directly from Hostaway, caches those reads for seven days, and retains their actual observation dates. Retrospective reads classify final historical availability; they are never treated as earlier booking-pace observations. Older source API restrictions do not suppress reservation-backed revenue or guest-night history. Reporting grants are an independent historical visibility boundary, not invitation activation dates. Changing a grant requires an explicit staff/user decision; a deployment must never widen unrelated accounts.

USD accommodation charges sum included accommodation components (including extra-person room charges) and included standard room discounts. Reconciliation recognizes both gross totals and channel totals net of an explicitly reported host commission. Zero-valued optional fields cannot invalidate a stay. Included refunds/resolutions are reconciled but kept separate from room charges: the dashboard flags affected stays instead of guessing their room/tax/fee allocation. Unknown financial components remain unresolved. Reference: [Hostaway standard financial fields](https://support.hostaway.com/hc/en-us/articles/360059842193-Financial-Reporting-Full-List-of-Standard-Fields) and [room coupon discounts](https://support.hostaway.com/hc/en-us/articles/360051963433-Reservations-Manage-Discount-Coupons). Generic `taxAmount` is never used as a substitute for finance components.

Partner channels can supply the host commission in `channelCommissionAmount` instead of a `hostChannelFee` finance component. The worker uses the explicit reservation commission only when the component is absent, and only when it reconciles the source total to the cent. This preserves gross accommodation charges without double-counting commission. A zero total or deleted room charge alone never proves a complimentary stay.

For legacy imports or documented complimentary stays, a database administrator may record an explicitly reviewed USD accommodation amount in `owners.finance_reconciliations`, with evidence references, reviewer, timestamp and an audit event. Only sanitized financial evidence references belong here, never guest names, notes, message text or payment credentials. The worker has SELECT only; the owner web role has no access. A correction fills an unresolved amount only when both the source-row fingerprint and a digest of the identity/dates/financial components still match. Fresh valid source finance takes precedence. New reviews and revocations invalidate the associated cached result on the next preparation; normal source changes invalidate it too. Deploy the additive table and updated worker grants before refreshing. Keep actual reservation corrections and supporting evidence out of the public repository.

Source stay nights exclude checkout and distribute integer cents deterministically across months. Cancelled stays and inquiries do not generate accommodation charges. Overlapping confirmed reservations withhold conflicting metrics. Owner stays and custom iCal blocks are excluded from guest occupancy. Validated subtotals survive missing reservations or homes, with explicit coverage counts; incomplete totals and incomplete year-over-year percentage changes are never presented as complete.

Occupancy uses guest nights divided by sellable physical-unit nights when calendar coverage is complete. Otherwise the dashboard retains known guest-night counts and explicitly labels the percentage of all calendar nights. It does not silently assume missing availability history means zero blocks. Backfilled calendar coverage and blocked nights are disclosed. Alternative listings are one physical unit: any available alternative keeps it open; every alternative must be blocked to classify it closed.

Planning ranges prefer seasonal pickup at matched lead times from the same month and adjacent months in up to three prior years, requiring complete final calendar coverage for each historical month, valid reservation/cancellation dates and at least 30 eligible nights. Recent open-to-booked conversion across 90 completed stay dates is a fallback when the seasonal sample is insufficient. Retrospective calendars supply final outcomes only. Current available-night rates translate conversions into revenue; gaps below minimum stay are excluded. A separate cancellation allowance uses at least 30 historical reservations still held at a comparable lead in the same season. When unavailable, the UI explicitly says existing bookings are assumed to remain. These are planning scenarios, not calibrated confidence intervals or payout guarantees. Stale data suppresses forecasts. Comparisons use prior completed accommodation charges, not fabricated historical booking pace.

### Property care and owner requests

Install `owner_portal.care.CARE_VIEW_SQL` as an administrator before applying worker grants. The worker-only view exposes fixed cleaning/maintenance categories, status transitions and dates for explicitly mapped physical properties; it omits ticket titles, guest fields, notes and messages. Only recorded status transitions establish a completed count. The owner API emits fixed labels and counts, never source ticket identifiers. Historical open work uses recorded month-end state.

**Owner access → Owner requests** lets approved human staff explicitly publish an owner-safe title, description and optional USD amount to one account/property. Owners can approve or ask to discuss; this records a decision only, without charging money, sending messages or starting work. Every response rechecks active membership, property/date grants and performance permission; requests are locked against duplicate responses. Revocation/withdrawal immediately removes access. The web role can update only response columns, not request scope, text or amounts.

### Statement publication

Approved human staff use **Owner access → Publish statements**. The workflow selects an approved/exported revision, checks a completed period, reconciled USD summary with no pending review items, maps every source home to an owner property, and requires account grants covering the entire period and every property. Legacy revisions did not freeze listing scope: the publisher must explicitly review the source revision and confirm the displayed homes/recipient before publication. A changed scope fails on submit. This manual check is essential for legacy revisions; a matching current portfolio label or listing count alone is not evidence of historical scope.

Publication copies only named financial totals, account/property display names, dates, recipient/property IDs and version into `owners.published_statements`. It never exposes source workbooks, receipts, guest-level rows or internal notes. Versions are immutable through the application; a newer revision creates a new version. Withdrawal retains the audit record while removing owner access. Repeated submission of the same recipient/revision is rejected. An owner needs the separate statements permission and current grants to every frozen property for the full interval, including at download time. Publication does not confirm payment. The owner can open, print/save PDF, or download a self-contained HTML statement without session tokens or source identifiers.

Administrators can also **Upload a finalized PDF** for statements completed outside bookkeeping. The upload requires an explicitly reviewed owner, exact property scope, completed month, USD totals that reconcile, and confirmation that the PDF contains no guest/private content. PDFs are bounded to 5 MB and stored outside public static assets in `owners.statement_documents`; the web role has read-only access. Every download rechecks full statement scope and current permissions before loading bytes. Downloads use an attachment filename generated by the server, private/no-store headers and a sandbox CSP. Duplicate PDF publication to the same account/month is rejected. No statements are fabricated or automatically uploaded when a recipient has no finalized document.
